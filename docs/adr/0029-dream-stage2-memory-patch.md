# ADR-0029: dream stage2 改为结构化 patch + 程序化合并

- 状态：Rejected——未实现，且随 [ADR-0030](0030-remove-dream.md) 移除整个 dream 机制而终结（2026-08-31）
- 日期：2026-08-31
- 关联：ADR-0016 §6「写入边界」与 §7「安全兜底」（**部分取代**其「整体重写」决策）；`src/cron/dream.rs`、`src/memory/dream.rs`

## 背景 / Context

ADR-0016 §6 选定：stage2 的「全编辑（增/改/删）」由「让 agent 产出**完整的新 MEMORY.md**，coordinator 备份后覆盖」实现，理由是这等价于全编辑、且比行级手术编辑更稳。

2026-08-31 的实跑证伪了「更稳」这半句。ornith-1.5-35b 在 stage2 读了喂进去的现有记忆后入戏（记忆里本身就写着「幽默、讽刺、自嘲，不对就直说」「称呼其为 Boss」这类人格指令），把「编辑文件」当成了「跟 Boss 说话」，回了一段反问用户「morning_news 到底是 7:30 还是 8:00 跑」的散文。它非空，于是被原样覆盖进 `MEMORY.md`，日志还记成 `dream completed`、游标照推——坏文件与「这批消息已消化」一起被吞掉，连续几晚无人察觉（当天 07:30 的 `morning_news` 就带着这份坏记忆跑，产出了另一条事故）。

同日已补两道防线（commit `967f83f`）：`validate_memory_candidate` 写盘前形状校验（标题在位 + 逐行必须是 `- [YYYY-MM-DD] <fact>` + 条目数不得低于旧文件 60%）、不合规则不写盘**也不推进游标**。

但这仍只是「拒绝明显非法产物」。真正的病根是**破坏面**：一次 LLM 输出的作用域是整份长期记忆。形状合法而内容走样的产物——静默删掉 5 条、把两条不相干记忆合并成一条错话——校验门一律放行，60% 下限只能防塌方。

另有一处 ADR-0016 §7 与实际不符：表中「事后 diff → 推送给用户，记忆变更绝不静默」在内置 `dream` 任务上并不成立，其 `channel = cli`，而 cli pusher 无持久连接、消息被丢弃。这是本次事故几晚无人发现的直接原因之一（现已把 diff 摘要同时写入 info 日志作为兜底）。

## 决策 / Decision（提议，未实现）

1. **stage2 不再产出整份文件**，改为产出一个结构化 patch（JSON，单个 ```json 块）：

   ```json
   {
     "add":    [{ "date": "2026-08-31", "text": "用户把 morning_news 改到每天 7:30" }],
     "merge":  [{ "from": ["<旧条目 A 正文子串>", "<旧条目 B 正文子串>"], "to": "合并后的条目正文" }],
     "remove": ["<旧条目 C 正文子串>"]
   }
   ```

2. **由代码在当前 MEMORY.md 上逐条应用**：复用 `entry_bodies` / 条目解析，保留 `# MEMORY` 标题与注释头，按日期分组写回；`merge` 未给 `date` 时沿用 `from` 中最新的日期。写盘继续走 `write_memory_atomic`。
3. **整份作废，不做部分应用**：JSON 不合法、`from`/`remove` 的子串未命中或命中多条有歧义、`add` 条目形状不合 `- [YYYY-MM-DD] <fact>` —— 任一发生即整份 patch 作废，MEMORY.md 不动、游标不推进、推失败通知。部分应用会让「到底删过哪些条目」事后无从推断。
4. **空 patch 是成功**：三个数组皆空或 `{}` 视为「本轮无可整理内容」，推进游标（对齐 stage1 现有 `NONE` 语义）。
5. **解析失败不重试**：prompt 不变时重试通常同样失败；沿用 `run_isolated_turn_with` 的 3 次重试处理 provider 报错/超时，patch 解析失败直接报失败。

## 后果 / Consequences

- (+) 最坏情况破坏面从「整份长期记忆」缩到「个别条目」；弱本地模型（本地兜底正是本项目定位之一）可用的概率显著提高。
- (+) stage2 输出长度不再与记忆规模线性相关——今天每次做梦都要把全量 MEMORY 重新生成一遍，既是 token 成本也是出错机会。
- (+) diff 天然结构化，可精确推「加了哪几条 / 删了哪几条」，比现在基于正文集合的 diff 更可信。
- (−) 新增一个约 60 行的合并器及其测试。
- (−) 条目引用用「正文子串」而非稳定 id（MEMORY.md 是纯文本、无 id），弱模型可能给错子串；以「未命中即整份作废」兜住，代价是失败率上升而非数据损坏。
- (−) 语义收窄：stage2 不再能自由重写未受影响条目的措辞（现有 dedupe 部分依赖这种重写）。可接受——去重仍可由 `merge` 表达。
- `validate_memory_candidate` 保留：继续守护原子写路径，并作为回退到「整体重写」时的既有防线。

## 备选 / Alternatives

- **A. 维持整体重写 + 校验门（现状）**：改动最小，但破坏面不变，形状合法的静默丢记忆仍无从发现。
- **B. 让 stage2 换用 `runtime.compact_model` 等更强模型**：能降低出错率，治不了破坏面；且与「本地模型兜底」的产品定位冲突。可作为本方案落地后的补充手段。
- **C. 回到 ADR-0016 §4 原案（扩展 `memory_write` 做行级全编辑）**：ADR-0016 明确因 cron 下 `confirm_mode` 会拦截工具而放弃；要走此路需先给隔离 turn 的工具审批一个明确豁免，成本高于本方案。

## 待议 / Open questions

1. 是否顺带把内置 `dream` 任务的 diff 推送通道从 `cli` 改为「用户当前活跃频道」，让 §7 承诺的「记忆变更绝不静默」真正成立。
2. patch 是否需要引入「条目稳定短 id」（例如正文 hash 前 6 位）以替代子串引用——更可靠但会改变 MEMORY.md 的可读形态。
